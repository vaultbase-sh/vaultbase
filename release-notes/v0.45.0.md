## Typed helpers in hook files, form bodies and the caller's address in custom routes

v0.45.0 comes from feedback on a full app rebuilt on Vaultbase. Hook files get real types for `ctx.helpers`, custom routes get the caller's address and parsed form posts, and a settings key that nothing reads is reported instead of being stored in silence. One small change in behaviour for custom routes that take form posts; see the upgrade notes.

## Added

- **`ctx.ip` in custom routes**: the caller's address, the same value the request log records. It is the connection's address, or the one a trusted proxy forwarded, and `null` when it isn't known. See [custom routes](https://docs.vaultbase.dev/concepts/hooks/#custom-http-routes).
- **Types for `ctx.helpers` in hook files.** `vaultbase.d.ts` in the hooks folder typed `helpers` as `any`; it now types every helper, with `ctx.auth` and a route's `ctx.ip`. A copy written by an earlier version is rewritten on the next start.
- **Admin code editor:** autocomplete and hovers for `helpers.sql`, `helpers.flags`, `helpers.webhooks`, `helpers.notify` and `helpers.uuid`, which had no types.

## Changed

- **Form posts to custom routes are parsed.** For `application/x-www-form-urlencoded`, `ctx.body` is an object of the form's fields, with the last value for a name sent more than once. It used to be `null`. `ctx.req` can still be read, for every value or the raw text.

## Deprecated

- **Settings keys that nothing reads.** `PATCH /api/v1/admin/settings` stores any key, so a typo such as `auth.password.min_length` (for `password.min_length`) answered 200 and changed nothing. The key is still stored, and the response now names it in a `Vaultbase-Warning` header (a `warning` in the result of the MCP `update_setting` tool); the server log names it once. These requests will answer 400, no sooner than two minor releases from now. See [settings](https://docs.vaultbase.dev/reference/settings/#reading--writing).

## Fixed

- **Request log:** a custom route that returns a `Response` was logged as 200 whatever status it sent. The log records the status sent.
- **Hook files:** a package installed after an import of it had failed stayed "Could not resolve … Maybe you need to bun install?" until a restart. The restart is still needed, and the error now says so.
- **The release binary** no longer prints `[Sucrose] warning: unexpected isContextPassToFunction error` on the first admin request.

## Docs

- New: [how fields are stored](https://docs.vaultbase.dev/concepts/databases/#how-fields-are-stored) on SQLite and Postgres (column types, and that relations are not foreign keys), and a [Claude Code](https://docs.vaultbase.dev/concepts/mcp/#claude-code) setup for MCP.
- Clearer: hook file imports and why two files don't share a module's state, which custom route answers when several match, and what additive snapshot apply leaves alone.

## SDKs

No SDK release is needed. JS SDK 0.11.1, and Dart `vaultbase` 0.7.1 with `vaultbase_flutter` 0.1.6, work with this release.

See the [changelog](https://docs.vaultbase.dev/changelog/) for the full list.

## Upgrade notes

- **Custom routes that take form posts:** a route that parses the form itself only when `ctx.body` is empty (`ctx.body ?? …`) now gets the parsed object. Use `ctx.body`, or read `ctx.req` without that check.
- **Settings:** if a settings update answers with a `Vaultbase-Warning` header, fix or remove the keys it names. An extension that reads settings of its own declares them with `registerSettingKeys` from `src/extend.ts`.
- **`vaultbase.d.ts`:** a hooks folder kept in git shows a one-time diff for this file after the upgrade. Commit it.
- Upgrades are supported from v0.24.0; from an older install, upgrade to 0.24.x first.
