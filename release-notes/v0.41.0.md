## MCP finds the right data, and the public surface is pinned

v0.41.0 fixes `vaultbase mcp` starting on the wrong data folder, and adds a test that catches changes to the public API before they ship.

## Fixed

- **`vaultbase mcp` reads the service's env file, as `token` does.** Run as the service's user on a Linux install, it opened `./vaultbase_data` in the directory it was started from instead of the service's data, and refused the token with "token verification failed". It now reads `/etc/vaultbase/vaultbase.env` (or `VAULTBASE_ENV_FILE`) for variables not already set, like `doctor`, `backup`, `token` and `wipe`.
- **MCP client configs set the data folder.** An MCP client such as Claude Desktop starts `vaultbase mcp` from its own directory, so without `VAULTBASE_DATA_DIR` it opened an empty install. The [MCP docs](https://docs.vaultbase.dev/concepts/mcp/) and the admin's local-binary snippet on `/_/mcp` now set it, and point service installs at the `@vaultbase/mcp` bridge, which needs no data folder.
- **The MCP `run_sql` tool says which database it runs on.** Its description said "the live SQLite DB" on Postgres servers too.

## Tests

- **The public surface is pinned.** A new golden test fails the build when the HTTP route table, the OpenAPI document or the MCP tool list (names, scopes, input schemas, resources, prompts, protocol version) changes. It runs on SQLite and Postgres against the same files, so the surface can't differ by database. This is the first part of gate 2 on the [road to 1.0](https://docs.vaultbase.dev/roadmap/).

## SDKs

No SDK release is needed. JS SDK 0.10.0, and Dart `vaultbase` 0.6.0 with `vaultbase_flutter` 0.1.5, work with this release.

See the [changelog](https://docs.vaultbase.dev/changelog/) for the full list.
