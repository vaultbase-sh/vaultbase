## Backups keep your uploaded files

v0.34.0 makes scheduled backups keep the uploaded files too, so a restore brings back the records and the files they point at, together.

## New

- **Backups keep the uploaded files.** With local file storage, scheduled and **Back up now** backups also keep the files in `uploads/`.
  - **Each file is stored once.** A manifest next to each snapshot lists the files, and their contents go in a store shared by every backup. After the first backup, a run copies only the files uploaded since.
  - **Restoring a stored backup puts back** every file that's missing or whose contents differ, and says how many.
  - **Pruning** removes stored files no remaining backup lists.
  - **The S3 copy mirrors the same layout.** After losing a server, sync the bucket prefix into the new server's `backups/` folder and restore from the admin, database and files together.
- **How it runs:**
  - It doesn't hold up requests while it runs.
  - A file that can't be read is left out and reported in the backup's status; it doesn't fail the backup.
  - One backup runs at a time, across cluster workers too.
- **Settings:** on by default, under **Settings → Backup & restore** → *Include uploaded files* (`backups.files`). With S3 file storage there's nothing to add, since the files already live off the server.

See [Backups → Uploaded files](https://docs.vaultbase.dev/guides/backups/#uploaded-files) and the [changelog](https://docs.vaultbase.dev/changelog/).

## Upgrade notes

- **The first backup after upgrading copies every uploaded file** into `<dataDir>/backups/files/`, so it needs about as much free disk as the uploads folder takes. Later backups copy only new files. Turn it off under **Settings → Backup & restore** if you back the uploads up another way.
- Upgrade notes for earlier releases apply if you are coming from before [v0.30.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.30.0).
