## Your own record ids, creates that are safe to repeat, and a failed snapshot apply that says so

v0.46.0 is for apps that make records before they reach the server, and for deploy scripts. A create keeps the `id` the client sends, an idempotency key makes a repeated create return the first record instead of making a second, and a snapshot apply that failed for a collection answers `422` instead of `200`. Two changes need a look before upgrading; see the upgrade notes.

## Breaking

- **`POST /api/v1/admin/migrations/apply` answers `422` when a collection failed to apply.** It used to answer `200` with the failure only in `data.errors`, so a deploy script that checked the status went on with a half-applied schema. The report is unchanged and still under `data` (`created`, `updated`, `skipped`, `errors`), next to `error` and `code`. The collections that didn't fail are still applied. `vaultbase --apply-snapshot` already exited with 1 in this case.

## Changed

- **An `id` sent on a create is used.** It was replaced in silence by one the server made. It has to be a UUID (`422` with `details.id` otherwise) and free: `409` when a record has it, and `409` when a deleted record's history still holds it. Without an `id` the server makes one, as before. This holds for `POST /api/v1/<collection>`, creates in a batch, `helpers.records.create` and the MCP create tools; auth collections still create users through `/register`. See [your own id](https://docs.vaultbase.dev/api/records/#your-own-id).

## Added

- **`X-VB-Idempotency-Key` on a create makes it safe to repeat.** The same key again, from the same caller on the same collection, answers `200` with the record the first request made and a `Vaultbase-Idempotent-Replay: true` header. No second record is made and no hook runs again. The same key with a different body answers `422`; while the first request is still running, `409`; once that record is deleted, `404`. A create that fails frees its key. Keys are kept for 24 hours, in the database, so several servers on one Postgres share them. Creates in a batch, custom routes and the auth endpoints don't read the header. See [idempotency key](https://docs.vaultbase.dev/api/records/#idempotency-key).
- **Logs: the reason a custom route failed.** When a route throws, the reason is in the admin's Logs page as a line next to the request's `500` (`route GET /path → 500: …`). It was only on the server's standard output. The caller still gets `Internal error` and nothing else.

## Fixed

- **Realtime from a browser on another origin:** an origin listed under Settings → CORS can open the WebSocket and the SSE stream. Only `security.allowed_origins` was checked, which no admin screen sets, while the refusal's hint and the quick start said to add the origin to the CORS setting. `security.allowed_origins` still works.
- **`Retry-After` across origins:** browser code on another origin can read the `Retry-After` header of a `429` or a maintenance `503`. It wasn't exposed, so a browser could only guess how long to wait.

## Docs

- New: [using the API without an SDK](https://docs.vaultbase.dev/api/without-sdk/), for clients that call the HTTP API directly: sessions and refresh, records, files, realtime, errors and retries.

## SDKs

- **JS SDK 0.12.0** adds `create(data, { idempotencyKey })`, and `vb-migrate` returns the report of a failed apply from the `422`.
- JS SDK 0.11.1 keeps working: its `vb-migrate` stops with `apply failed: 422` where it used to print the report. Dart `vaultbase` 0.7.1 and `vaultbase_flutter` 0.1.6 work unchanged, and send an `id` of your own like any other field. The Dart SDK has no option for the idempotency key yet.

See the [changelog](https://docs.vaultbase.dev/changelog/) for the full list.

## Upgrade notes

- **Snapshot apply:** treat a non-2xx answer from `POST /api/v1/admin/migrations/apply` as a failed deploy, and read `data.errors` from it for the reasons. A script that read `data.errors` from a `200` must read it from the `422` too.
- **Creates that send an `id`:** a client that builds a new record from a fetched one must leave `id` out. Sent along, it now answers `409` instead of making a copy under a new id. An `id` that isn't a UUID answers `422`.
- Upgrades are supported from v0.24.0; from an older install, upgrade to 0.24.x first.
