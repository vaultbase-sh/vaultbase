## Security release

v0.13.2 fixes several authentication and authorization issues. Upgrade if you use API tokens, Sign in with Apple, or custom routes.

## Upgrade notes

- **API tokens are limited to their scopes on the data API.** Records, batch, files, realtime and custom routes used to treat every API token as the admin who created it. Now:
  - `admin` keeps full admin access.
  - `read` can read everything but not write.
  - `write` can create, update and delete under collection rules, as a non-admin.
  - Any other scope (for example only `mcp:*`) is treated as anonymous.

  If a token calls these endpoints, make sure it has `read`, `write` or `admin`.
- **API tokens can't be refreshed.** `/auth/refresh` returns `401` for them.
- **File download tokens are not sessions.** They work only on the file download they were issued for.

## Security fixes

- An API token with any scope could act as full admin on records and files, and `/auth/refresh` turned it into an unscoped admin session.
- Sign in with Apple trusted the `id_token` without verifying it. It is now checked against Apple's published keys (RS256 signature, issuer, audience = your Services ID, expiry).
- Tokens of logged-out or deleted users still worked on the TOTP, recovery-code, email-verify, anonymous-promote and OAuth2 link/unlink endpoints, and a token from one auth collection was accepted on another's routes.
- Revoked or force-logged-out admin tokens still worked for collection create / update / delete and for admin impersonation.
- Custom routes accepted revoked tokens.
- A forged API token could overwrite a real token's last-used IP and user agent in the token list.
- The `/metrics` bearer token is compared in constant time.

## Other changes

- Removed the UPX compression scripts; UPX-packed binaries crash on start.
- `vaultbase --help` no longer claims the encryption key can be read from a file. It comes from `VAULTBASE_ENCRYPTION_KEY` only.
