## Sign-up hooks, password and encrypted fields

v0.32.1 fixes how sign-up runs `beforeCreate` hooks, and how `password` and encrypted `editor` fields are stored.

## Fixed

- **Sign-up answered differently for a taken address when a `beforeCreate` hook refused the payload.**
  - The hook now runs, and what it returns is validated, before the address is looked up.
  - The collection's own password and encrypted fields are prepared on both branches, so a taken address no longer answers faster.
- **An email set by a `beforeCreate` hook was ignored** at sign-up and on invitations. The account now gets the hook's address, which is validated and checked for an existing account.
- **Sign-up could make accounts without an email** when the email field was made optional or a hook removed the address. It answers `422`.
- **A `password` field stored a value that looked like a hash as sent,** skipping hashing and the field's length rules. Every value is hashed now.
- **An `encrypted` `editor` field was stored in the clear;** only record history encrypted it.
  - It is encrypted in the table now. Values stored before stay readable and are encrypted when next written.
  - The admin offers the option on editor fields.

## Changed

- **A field can't be both `unique` and `encrypted`.** Encrypted values never repeat, so uniqueness was never enforced on them. A schema saved with both keeps them.

See the [changelog](https://docs.vaultbase.dev/changelog/) for everything.

## Upgrade notes

- `beforeCreate` hooks on auth collections now run for every sign-up, including one whose address already has an account. That sign-up is then dropped without telling the caller. Put side effects, such as creating records or sending mail, in `afterCreate`.
- Filters and rules on an `encrypted` `editor` field match only values stored before this release, as on other encrypted fields.
- Upgrade notes for earlier releases apply if you are coming from before [v0.30.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.30.0).
