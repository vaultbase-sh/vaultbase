## Extensions and hooks as files

v0.19.0 makes Vaultbase extensible from code and lets you keep hooks, routes, cron jobs and queue workers as files next to your data. **Read the upgrade notes**: creating a hooks folder moves the hooks you wrote in the admin UI into it.

## New

- **Hooks as files.** Create a `vb_hooks/` folder next to the data directory (or set `VAULTBASE_HOOKS_DIR`) and each file in it defines one hook, route, cron job or queue worker with `defineHook` and friends. Files can import each other and npm packages installed in the folder, reload within a second of a change, and keep their previous version running if a change fails to load (the error shows in the admin UI). The admin UI and the MCP tools edit the same files, and a save is refused (409) if the file changed on disk since it was opened. `vaultbase.d.ts` in the folder types the `ctx` argument.
- **Extension points.** Field types, OAuth2 providers, storage drivers, email transports and push providers are registries (`registerFieldType`, `registerOAuthProvider`, `registerStorageDriver`, `registerEmailTransport`, `registerPushProvider` in `src/extend.ts`). Pick a registered storage driver or email transport with the `storage.driver` / `email.transport` setting.
- **Event bus.** Record writes and sign-ups emit `record.created`, `record.updated`, `record.deleted` and `auth.signup`; listen with `on()`. Realtime, webhooks and after-hooks now run as listeners, with unchanged behaviour.
- **Hooks, routes, jobs and workers from code** (`registerHook`, `registerRoute`, `registerJob`, `registerWorker`), alongside the ones from the admin UI.
- `GET /api/v1/admin/extensions` lists everything registered.

## Improvements

- List requests are a little faster (about 4–9% in a local load test).
- The README and deployment guide now say cluster mode only adds throughput on Linux; on macOS and Windows one worker takes every connection.

## Upgrade notes

- **Creating a hooks folder moves admin UI code into it.** On the first start with a hooks folder, hooks, routes, jobs and workers written in the admin UI are moved into it as files, keeping their ids. One whose code doesn't load as a file stays in the database and the server logs why. To keep everything in the database, don't create the folder, or set `VAULTBASE_HOOKS_DIR=off`.
- **New fields must use a registered type.** An unknown field type (a typo, say) is refused instead of being stored as text. Existing fields are unaffected.
- **`storage.driver` and `email.transport` must name a registered driver or transport.** An unregistered storage driver is now an error instead of silently falling back to local disk.
