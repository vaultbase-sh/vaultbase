## Maintenance mode and view parameters

v0.35.0 adds a maintenance mode that closes the API to clients while the admin keeps working, and parameters on view collections, so one view can answer for any date range or user.

## New

- **Maintenance mode.** Switch it under **Settings → Maintenance mode**; a banner on every admin page shows while it's on.
  - **Clients get `503`** with your message, and a `Retry-After` when you set a time to be back. The JS SDK reports it as `kind: "maintenance"`, the Dart SDK as `MaintenanceException`.
  - **Read-only** keeps reads and realtime working and refuses writes. Fully off also closes clients' realtime connections; the SDKs reconnect when it ends.
  - **Still open:** admin sessions, admin API tokens, MCP and `/api/health` (which reports the level). Custom routes are closed unless you leave them open one by one.
  - **Background work:** cron jobs, queue workers and webhook deliveries pause unless you keep them running. Record hooks always run. The orphaned-upload sweep doesn't run during maintenance, so a migration that drops a file's reference for a while doesn't lose the file.
- **Parameters on view collections.** A view's query can use `:name` placeholders, filled from the request as `?params[name]=…` on list, get-one, `_aggregate` and CSV export.
  - Each parameter has a type (`text`, `number`, `bool`, `date`) and a default, or is `required` (a read without it gets `400`). Values are always bound behind a cast, never written into the SQL.
  - `from: "auth.id"` fills a parameter with the signed-in user's id, which the request can't set, for per-user views.
  - Rules read the values as `@request.query.params.<name>`.
  - In the admin, the view editor has a parameters table under the query and previews with test values; a view's records page and its CSV export take parameter values.
  - The JS SDK takes `params` and `vb-types` emits a `<View>Params` type; the Dart SDK takes `params:` and its codegen emits a `<View>Params` class.

## Changed

- **Faster start on Postgres.** Checking the built-in tables at start takes two catalog queries instead of one per table, and a fresh install creates its tables and indexes in two statements.

## Fixed

- A realtime connection with no subscriptions wasn't told its sign-in expired.
- A setting changed outside the settings API could read as its old value for up to 2 seconds.

See [Maintenance mode](https://docs.vaultbase.dev/guides/maintenance/), [Collections → Parameters](https://docs.vaultbase.dev/concepts/collections/#parameters) and the [changelog](https://docs.vaultbase.dev/changelog/).

## Upgrade notes

- **Nothing to do.** The first start adds a column for view parameters to the collections table; maintenance mode is off until you turn it on.
- The SDK features need the new SDK versions: JS SDK and Dart SDK releases follow this one.
- Upgrade notes for earlier releases apply if you are coming from before [v0.30.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.30.0).
