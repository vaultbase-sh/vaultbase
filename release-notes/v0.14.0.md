## Scheduled backups

Settings → Backup & restore can now back up the database on a schedule:

- **Schedule**: a cron expression in UTC (default `0 3 * * *`, daily at 03:00).
- **Keep**: the newest N snapshots are kept (default 7); older ones are deleted after each run.
- **Copy to S3**: optionally upload each snapshot to an S3-compatible bucket (AWS S3, Cloudflare R2, Backblaze B2, MinIO). It has its own credentials, separate from file storage. Use a private bucket: snapshots contain password hashes and settings.

Snapshots are written to `<dataDir>/backups/` with SQLite `VACUUM INTO`, so they are consistent while the server keeps taking writes. The same page lists stored snapshots with download, restore and delete, shows the last run, next run and last error, and has a **Back up now** button. In cluster mode only one worker runs each scheduled backup.

New admin endpoints:

```
GET    /api/v1/admin/backups
POST   /api/v1/admin/backups
GET    /api/v1/admin/backups/<name>
DELETE /api/v1/admin/backups/<name>
POST   /api/v1/admin/backups/<name>/restore
```

Uploaded files are not included in snapshots. Back up `<dataDir>/uploads` separately if you use local file storage.

## Fixes

- `GET /admin/backup` streamed the live database file, which could miss recent writes still in the WAL. It now returns a consistent snapshot.
- The S3 storage secret (`s3.secret_access_key`) was stored in plaintext even with `VAULTBASE_ENCRYPTION_KEY` set. It is encrypted the next time storage settings are saved.
- Restore could fail on Windows with `EBUSY` because the old database handle was not released.
