## Files from hooks, a public folder for your web app, and rules that read other collections on single records

v0.48.0 lets hooks, routes and workers download binary files and store them on a record, makes the accepted upload types a setting, and serves a web app from the server's root. Rules that use `@collection.*` or `_via_` now work on view, update and delete by id the way they work in lists. That last change can allow requests that were refused before; see the upgrade note.

## Added

- **Binary downloads in `helpers.http`.** `helpers.http.request({ ..., responseType: "bytes" })` returns the body as a `Uint8Array` (`bytes`) instead of `text` and `json`, so a hook or worker can download an image or another binary file without it being mangled as text. `helpers.http.getBytes(url, headers?, opts?)` does a GET and throws on a non-2xx status, like `getJson`. A body over `maxBytes` (default 50 MB, at most 512 MB) throws instead of being read into memory. Egress checks, retries and the timeout work as for text. See [`helpers.http`](https://docs.vaultbase.dev/concepts/hooks/#helpershttp).
- **`helpers.files.save`** stores a file on a record's file field from a hook, custom route, cron job or queue worker: `helpers.files.save(collection, recordId, field, data, { name?, type? })`. It makes the same checks as an upload, writes through the configured storage (local or S3), and sets the field through `helpers.records`, so hooks, record history, realtime and webhooks run. A multi-file field gets the file added, also when several saves run at once; a single-file field has its value replaced. See [`helpers.files`](https://docs.vaultbase.dev/concepts/hooks/#helpersfiles).
- **Conditional writes in `helpers.records`.** `update(collection, id, data, { filter })` and `delete(collection, id, { filter })` write only when the record matches the filter, checked under the record's lock just before the write, so two workers can't both claim the same job. A filtered update answers `null` when the record doesn't match. `delete` now answers `true` when it deleted a record and `false` otherwise (it answered nothing before). See [conditional writes](https://docs.vaultbase.dev/concepts/hooks/#conditional-writes).
- **Allowed file types are a setting.** Under **Settings → File storage → Allowed file types** (`files.allowed_types`) an admin ticks the types uploads may have: images, PDF, text, Markdown, Office and OpenDocument files, JSON, CSV, XML, archives, audio and video. Other types get `415`, from the files API and from `helpers.files.save`. HTML and JavaScript are never on the list. Left unset, it's the list as before plus Markdown, CSV and zip. Files that aren't raster images are still served as downloads. See [files](https://docs.vaultbase.dev/api/files/).
- **A public folder.** Static files in `vb_public/` next to the data directory (or the folder named by `VAULTBASE_PUBLIC_DIR`) are served from the server's root, so a web app built on Vaultbase can live at `https://example.com/`. It answers only what no route answered: `/api/*`, the admin, `/auth/*` and `/realtime` keep priority. `VAULTBASE_PUBLIC_SPA=1` serves `index.html` for client-side routes. Hashed asset names are cached for a year, everything else revalidates. Dotfiles (except `/.well-known/`) and links out of the folder aren't served. See [serving a web app](https://docs.vaultbase.dev/guides/deployment/#serving-a-web-app).

## Fixed

- **`@collection.*` and `_via_` on single records.** View, update and delete by id (also in a batch) and file access now ask the database for rules that read other collections, as a list does. Before, any comparison using one was false there, so a rule such as `@collection.accounts.owner = @request.auth.id && @collection.accounts.active = true` refused every request by id while the list served the same records. An update rule is still checked against the record as it stands and as the patch would leave it. Realtime delivery still treats such a comparison as false. See [cross-collection references](https://docs.vaultbase.dev/concepts/rules/#cross-collection-references).
- **`rule_denied` for rules that don't read the caller.** A `403` for a signed-out caller said `reason: "not_signed_in"` even when signing in couldn't help (`view_rule: active = true` on a record with `active = false`, say). It now says `rule_denied`. Rules that read `@request.auth` still answer `not_signed_in` to a signed-out caller.

## SDKs

No SDK release is needed. JS SDK 0.12.0, and Dart `vaultbase` 0.7.2 with `vaultbase_flutter` 0.1.6, work with this release.

See the [changelog](https://docs.vaultbase.dev/changelog/) for the full list.

## Upgrade notes

- **Rules that read other collections now allow single-record requests they used to refuse.** A view, update or delete rule using `@collection.*` or `_via_` gave `403` on every request by id (and in a batch, and for file access), whatever the other collection held; it now gives the answer the list gives. If an app relied on that refusal, for example a rule that was meant to work only in lists, make the rule say so (an update rule that should stay admin-only is `""`). Rules without `@collection.*` or `_via_` are unchanged.
- Upgrades are supported from v0.24.0; from an older install, upgrade to 0.24.x first.
