## Sign-up stores field values properly

v0.31.1 fixes how sign-up and invitations store an auth collection's own fields.

## Fixed

- **Sign-up stored custom field values as sent.** Registering, accepting an invitation, upgrading a guest account and OAuth sign-up skipped what a record write does: a `json` or multi-select value answered 500, an `encrypted` field was stored in the clear, a `password` field unhashed, and an `autodate` field took the client's value. They now store values as a record write does, and what a `beforeCreate` hook returns is validated at register and invite.
- **Invitations are checked as an admin's write, for the fields they set.** An invite with an email alone works when the collection has a required field.
- **A field marked required when its auth collection was created broke guest sign-up, OAuth sign-up and invitations** with a 500. New auth collections don't have the limit, and `required` is still checked wherever a body is validated.

See the [changelog](https://docs.vaultbase.dev/changelog/) for everything.

## Upgrade notes

- **Postgres:** nothing to do; the server removes the limit from existing auth collections when it starts.
- **SQLite:** the server log at start and `vaultbase doctor` name any affected fields. The [authentication docs](https://docs.vaultbase.dev/concepts/authentication/#required-fields-made-before-0311) show how to move each one to a new column and keep its values.
- Upgrade notes for earlier releases apply if you are coming from before [v0.30.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.30.0).
