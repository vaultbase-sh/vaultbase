## Fewer read workers by default, five fixes

v0.22.1 changes the read-worker default and fixes five bugs found in a review of the database layer. No configuration changes; collections created before this release get their `autodate` columns at the next start.

## Changes

- **Read workers default to cores minus two.** 0.22.0 started one per spare core. On a 4-vCPU host that left the main thread and the reverse proxy sharing a core with the third worker, and the box answered fewer requests than it did with two. The default is now cores minus two, at least one on two cores or more, none on a single core, at most 8. `VAULTBASE_READ_WORKERS` still sets the count outright.

## Fixes

- **`autodate` fields are stored.** They were computed and then skipped on the way to the table, which had no column for them. They now have a column, the server sets them on create and update per `onCreate` and `onUpdate`, a client-sent value is dropped, and existing collections get the column at the next start.
- **Renaming a field keeps its data.** The schema diff saw a new name, dropped the column and added an empty one. The admin editor now sends the previous name as `renamedFrom` and the column is renamed in place, with its unique index and search index following. API callers can send the same hint with `PATCH /api/v1/collections/<id>`.
- **Datetime macros compare correctly.** `@now`, `@todayStart` and the rest bound ISO-8601 strings while `date` and `autodate` fields hold Unix seconds, so SQLite's type ordering decided the comparison. They are Unix seconds now, in filters, rules and the in-process rule evaluator.
- **The 1,000-row cap on `_via_` back-relations applies.** It sat on the aggregate, where it capped nothing.
- **Connection-bound caches are cleared before `closeDb` returns**, not a few ticks later.
