## Time limits on scripts

v0.33.0 puts a time limit on every run of a hook, custom route, cron job and queue worker, so one stuck script can't hold its caller, its transaction or its worker indefinitely.

## New

- **Time limits on scripts.**

  | Script | Default | When the limit runs out |
  |---|---|---|
  | Before hooks | 10 s | the write fails with a `422` naming the hook |
  | After hooks | 30 s | the server log says so |
  | Custom routes | 30 s | the caller gets `504` |
  | Cron jobs | 5 min | the run is recorded as failed |
  | Queue workers | 5 min | the job fails and is retried as its worker says |

  When a run is stopped:
  - its `helpers.fetch` and `helpers.http` requests are aborted;
  - a `helpers.sql.transaction` it holds is rolled back;
  - its later `helpers` calls throw;
  - a queue job keeps its worker's slot until the script really ends, so stuck runs don't pile up.

  Set the limits under **Settings → Script time limits**; `0` turns a limit off. Code registered by an app embedding Vaultbase, and the server's own workers, have no limit.

- **Limitation:** scripts run in the server's own thread, so a loop that never awaits still can't be interrupted. A helper call already under way when the limit runs out, such as an email being sent, still finishes. See [Hooks → Time limits](https://docs.vaultbase.dev/concepts/hooks/#time-limits).

See the [changelog](https://docs.vaultbase.dev/changelog/) for everything.

## Upgrade notes

- **The limits apply as soon as you upgrade.** A cron job or queue worker that takes longer than 5 minutes, a route or after-hook longer than 30 s, or a before-hook longer than 10 s now fails. Raise its limit, or set it to `0`, under **Settings → Script time limits** before upgrading.
- **A cron or queue job stopped partway isn't rolled back:** what it did before stays done, and a retry starts over.
- Upgrade notes for earlier releases apply if you are coming from before [v0.30.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.30.0).
