## Shared commits and live monitoring

v0.20.0 changes how record writes reach the database and adds a Monitoring page to the admin UI. **Read the upgrade notes first**: writes that arrive together now commit together.

## Changes

- **Record writes share commits.** Creates, updates and deletes that arrive in the same event-loop turn run in one SQLite transaction and commit together. A write still returns only after the COMMIT that holds it; if that COMMIT fails, every write in it fails, and a statement that fails only undoes itself. Realtime events, webhooks and after-hooks run after the commit. Batches, cascading deletes and schema changes commit any open group first.
- **WAL checkpoints run on a background thread** with their own connection, so a request no longer pays for one. SQLite's own autocheckpoint is switched off while the worker runs and back on if it stops.
- **Monitoring page** in the admin UI (`/_/monitoring`, under Data): requests and writes per second, latency, CPU, event-loop lag, memory, the per-step latency breakdown, status classes, methods, SQLite file and WAL sizes, the checkpointer and realtime connections, refreshed every 1, 2 or 5 seconds.
- **`GET /api/v1/_/metrics` returns more**: read and write latency, status and method counters, the last 120 seconds per second, process gauges, SQLite file sizes and checkpointer stats. It no longer runs a WAL checkpoint each time it is polled. Write requests are timed per step, including a new `record_write` step.
- Record create, update and delete reuse cached SQL statements.
- **Fixed:** the enabled-hooks cache queried the hooks table twice on every record write.

## Upgrade notes

- **A write in a shared commit can be read by another request up to one event-loop turn before it commits.** It only disappears if that COMMIT itself fails (disk full, I/O error), and then the write's own request fails too. Set `VAULTBASE_GROUP_COMMIT=0` to commit every write on its own, as before.
- **Shared commits are off under `vaultbase cluster`.** An open group holds SQLite's write lock for its turn and other workers would wait on it, so each worker commits writes on their own. For write-heavy workloads, run a single process.
- The Prometheus output gains a `record_write` step label; nothing existing is renamed.
