## Stricter answers for bad tokens and unknown keys, collections in the sidebar

v0.44.0 turns the two warnings from 0.42 into errors, as announced: a token the server doesn't accept answers 401, and a key that does nothing answers 400. The admin also lists your collections in the sidebar, each with an icon for its type.

## Breaking

Both were announced in 0.42.0, which answered these requests as before and warned.

- **A Bearer token the server doesn't accept answers 401** on the records, files and batch APIs: `{"error":"Token expired or invalid","code":401,"reason":"token_invalid"}`. Until now the request ran as if no token had been sent, so a public read answered 200 and a refused one 403. An API token without the scope for the request answers 401 with `reason: "insufficient_scope"`; in a batch, one such operation refuses the whole batch. The check comes before anything is looked up, so the answer is the same whether or not the collection or file exists.
- **Unknown keys answer 400.** A list with a `sort`, `expand` or `fields` name that isn't a field, and a create or update with a body key that isn't a field, are refused, with each problem in `details`. They used to be ignored. Whatever a read returns is still accepted, so a fetched record can be saved back as it came, and `sort=@rank` for a search still works. View collections and the operations inside a batch aren't checked.

## Added

- **Collections in the admin sidebar.** Your collections are listed under "Collections", each opening its records, with the open one highlighted. A chevron hides or shows the list.
- **An icon for each collection type** (base, auth, view, singleton), in the sidebar, on the Collections page and on the type picker.

## Fixed

- **After-hooks:** a failed hook lookup (for example while the database was closing) is logged instead of going unhandled.

## SDKs

- **JS SDK 0.11.1** and **Dart `vaultbase` 0.7.1** handle the new answers: `token_invalid` refreshes the session once and otherwise reports it as expired; `insufficient_scope` is reported as forbidden, with the server's message, and keeps the token. API tokens are no longer refreshed or cleared by the SDKs. `vaultbase_flutter` 0.1.6 works unchanged.
- Older SDKs keep working. On a 401 they refresh or end the session, which is the right outcome for an expired token.

See the [changelog](https://docs.vaultbase.dev/changelog/) for the full list.

## Upgrade notes

- **Tokens:** treat 401 from the records, files and batch APIs as "sign in again". A client that sends a stale token with requests for public data must drop the token; such requests answered 200 before.
- **API tokens:** check that each token has the scope for what it does: `read` for reads, `write` for writes. A token without it was treated as anonymous before, and now answers 401.
- **Keys:** fix or remove the keys the `Vaultbase-Warning` header named in 0.42 and 0.43. The header is no longer sent for them.
- Upgrades are supported from v0.24.0; from an older install, upgrade to 0.24.x first.
