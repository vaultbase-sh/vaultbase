## Fixes from a technical review

v0.24.0 fixes every finding of an external technical review of v0.23.1: permissions that changed on schema sync, rules that decided differently for a list and a single record, partly committed batches, duplicate unique jobs, a live restore that broke read workers, and three races between servers sharing one Postgres database. Each one was reproduced first and has a regression test. Read the upgrade notes before upgrading: two of the fixes make requests fail that used to succeed.

## Upgrade notes

- **A write batch with a failed op now fails as a whole.** A batch op that hit a missing record or collection came back as a 404 entry while the ops before it committed. The batch now answers that status (`Batch failed at request N: …`) and changes nothing. Read-only batches still report each op.
- **Broken hook code now blocks writes.** An enabled `beforeCreate` / `beforeUpdate` / `beforeDelete` hook whose code doesn't compile was skipped, so the check it carried silently stopped. Its writes now fail with a 422 naming the hook. Such a hook has logged `[hooks] Failed to compile hook` at every start: fix or disable it before upgrading.
- **`strftime` in rules**: forms other than the codes `%Y %m %d %H %M %S %j` with a stored date and `'unixepoch'`, `'now'` or a literal timestamp now deny on single-record checks, as the list query does.
- **Duplicate active jobs with one `uniqueKey`** are settled at the first start: one keeps the key, the others keep running without it.

## Fixes

- **Schema snapshots keep permissions.** Syncing a snapshot without rules made an admin-only collection fully public, and exports left public rules out, so an import made them admin-only. Exports now write all five rules; a rule a snapshot leaves out keeps its current value on sync, and is admin-only when the snapshot creates the collection.
- **Date rules decide the same everywhere.** Single-record checks (get, update, delete, files, realtime) treated `strftime(...)` as empty, so some rules passed there while the list denied. They now evaluate it like SQL, and deny on anything they can't evaluate.
- **Inline code that doesn't compile is refused when saved** (hooks, routes, jobs, queue workers; admin API and MCP).
- **Write batches are all or nothing** for every kind of failure.
- **`uniqueKey` holds under concurrency**: a partial unique index allows one queued-or-running job per key.
- **Online restore with read workers.** After a restore, every read served by a worker failed with `disk I/O error` until a restart. Restore now stops the read workers and the checkpointer, swaps the file and starts them again, and checks the file first (422 for a damaged or foreign database).
- **Several servers on one Postgres (beta):**
  - Running jobs are leased; a server starting up no longer runs again a job another server is running, and a late finish can't overwrite a newer attempt.
  - If-Match holds across servers: two servers can't both accept one ETag.
  - Peer messages are sized in bytes. Multibyte records no longer cause lost cache invalidations (a rule change could stay unseen by other servers until a restart); a server that misses one resets its caches within 10 seconds.
- **Every MCP tool call is audited**, over HTTP/SSE and stdio.
- **The release workflow builds the tag it publishes**, and the SBOMs list the dependencies (they were empty).
- Failed log writes are counted and reported instead of swallowed.

## New

- **`GET /_/ready`**: checks the database, storage, read workers, queues and log writes; 503 when the server can't serve. Use it for load balancer and orchestrator readiness probes; `/_/health` stays the liveness probe.
- **Prometheus**: responses by status class, job and webhook backlogs, read worker counts, log write failures.
- File token responses say whether the token is one-time (`one_time`).

Pairs with `@vaultbase/sdk` 0.6.3, which fixes `iterate()` stopping after the first page, caching of one-time file tokens, generated date / null / vector / color types, and `ifMatch: "auto"`.
