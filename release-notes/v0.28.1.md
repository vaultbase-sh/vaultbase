## Read-only SQL on Postgres is read-only again

v0.28.1 is a security release for Postgres installs. SQLite installs are not affected, but get the other fixes below.

## Security

- **Read-only SQL on Postgres could do more than read.** The admin SQL page and MCP `run_sql` without `allow_write` (which needs only the `mcp:sql` scope) ran their SQL on one of the server's pooled connections, as the server's own database role. A setting a query made stayed on that connection and broke later queries landing there, and when the server's role was a superuser (the default with the official Postgres image) a query could reach programs and files on the database host.

  Read-only SQL now runs over a login of its own that can only read this install's schema. The server creates it the first time read-only SQL runs, when its role may create roles; otherwise name one in the new `VAULTBASE_PG_READONLY_URL`. Each run gets a connection of its own, a read-only transaction that is rolled back, exactly one statement (enforced by Postgres), its time limit, and at most 1,001 rows fetched through a cursor. A login that can do more than read is refused, and Vaultbase never falls back to the server's role. See [Read-only SQL on Postgres](https://docs.vaultbase.dev/concepts/databases/#read-only-sql-on-postgres).

- **`pg_dump` got the database password on its command line**, visible to other users of the host. It now gets it in `PGPASSWORD`.

## Fixes

- **Postgres: backups of a schema with capital letters in its name** dumped another schema, or nothing. The name is quoted now.
- **Postgres: the SQL page's schema panel** read a SQLite file, failing or showing a stale schema. It reads the Postgres catalog now.
- **Postgres: list totals after raw SQL writes** (a hook's `helpers.sql`, MCP `allow_write`) kept their old value until the next write through the API. Raw writes now report the table they touched.
- **MCP `allow_write` on Postgres** runs on a connection of its own, so a setting it changes doesn't stay on a pooled one.

## Upgrade notes

- **Postgres:** read-only SQL needs either a server role that may create roles (a superuser, or `CREATEROLE`) or a login named in `VAULTBASE_PG_READONLY_URL`; without either, the SQL page and MCP `run_sql` answer with the setup steps. `pg_hba.conf` must let the new `vb_ro_…` login connect like the server's own. Several servers of one install must share `VAULTBASE_JWT_SECRET`, as they already should.
- **Postgres:** a read-only query past 1,000 rows now shows "1,000+" rather than an exact total.
- Restoring a Postgres backup into another database or schema: add `--no-privileges` (`-x`) to `pg_restore`.
- The upgrade notes for [v0.27.0](https://github.com/vaultbase-sh/vaultbase/releases/tag/v0.27.0) apply if you are coming from an earlier version.
